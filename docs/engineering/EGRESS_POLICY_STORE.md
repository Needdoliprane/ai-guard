# E1 policy registry — internal engineering guide

[Français](EGRESS_POLICY_STORE.fr.md) · [Egress direction](EGRESS_CONTROL.md) · [Core contracts](EGRESS_SOFTWARE.md) · [Dated evidence](evidence/2026-11-13/egress-policy-store/README.md)

This guide describes the internal Rust policy registry and explicit SQLite format15 maintenance. The E1 R6 manifest identifies 29 source postimages over public `ceb7b1f`; the tested R5/R7 compositions also include four separately reviewed human-source corrections published in `328f3bc`. Results belong to those frozen compositions, not automatically to another checkout or a later commit. R5 records **14 PASS, one fixture FAIL and 12 NOT_RUN**; R7 records **13 PASS and an all-targets check PASS**, with 320 warning diagnostics. The first 14 parents were not rerun on R7. This is software validation, not production qualification or an operator command.

The registry retains policies in the existing SQLite database of the selected tenant. It provides immutable revisions, a current head, exact operation receipts and logical terminal reservations. It does not resolve names, connect sockets, issue connection permits, apply revocation to a runtime, expose an HTTP route or grant a human network permission. G05/G07/G11 remain open. `revoke_requested` never means that an existing connection was closed.

On the V1 candidate, `broker policy` uses the reserved technical API on a previously published Store15. The human Journal shows session policy replacements and revocation requests only to a context with access to that session's metadata. It labels the evidence as policy-registry coverage and leaves connection decisions to the runtime egress path. ## Authority and transactions

The private `Store::egress_replace_policy_scoped` and `egress_revoke_policy_scoped` methods require the actual retained `OwnedSourceToken`, a live `HumanSourcesWriteEpoch`, and an `AuthenticatedReviewRunnerCredential`. The same checked SQLite transaction verifies the source's physical backing, marker, incarnation and live review binding before operation lookup and again before commit. The effective actor is explicitly `machine_control`, with the authenticated credential and binding identity. The binding's human owner is not attributed as approver.

A request cannot choose a tenant, principal, clock, Store limits or reservation class. It binds a canonical operation UUID, selector and expected revision/epoch. A session replacement also binds the exact tenant policy revision, epoch and digest. Its Session resource must already exist and be active in this Store; its interval, exact destinations and limits must be within that retained tenant policy. Effective evaluation must continue to use the existing core's **current tenant ∩ current session**; this registry creates no runtime enforcement path.

Exact retry returns the original canonical receipt bytes without appending an event or changing a timestamp. Current source, actor and clock validation still precede that retry. A different payload under the operation UUID conflicts. Replacement increments revision and epoch; revocation increments the epoch once and retains the immutable revision. Revocation requires the exact active head and live control authority, and remains available after the old policy expires or its Session resource ends. Historical replay checks the tenant ceiling and active Session at the original replacement prefix.

Normal redaction runs before persistence. If it changes any canonical identity, policy destination, digest or event field, the whole mutation refuses. Policy destinations remain sensitive metadata. The private human read helper revalidates existing metadata rights and refuses redaction collisions; no public delivery or new read route is provided by this lot.

## Exact format 15 and maintenance

Format14 remains closed and unchanged. Format15 explicitly inherits its objects and facts, adding exactly `egress_policy_meta`, `egress_policy_revisions`, `egress_policy_heads`, `egress_policy_operations` and `egress_policy_reservations`. Ordinary legacy openers refuse both modern formats. Modern openers retain the genuine source token and require its declared format to equal the actual14 or15. The original13→14 source anchor and receipt remain intact.

The format15 reader selects ASCII case variants of this new egress family and refuses noncanonical names through the closed marker. Inherited families keep their canonical `GLOB` dispatch so ordinary historical variants are not promoted to authority. Corruption fixtures for this distinction establish no new worker/HTTP ingestion path. Genesis explicitly requires its original format14 anchor to be present in the preceding committed prefix: `0 < source_anchor.seq <= previous_seq < genesis_seq` with contiguous predecessor adjacency.

There is no automatic migration and no CLI migration command in this lot. Trusted maintenance glue must stop consumers, acquire the real `HumanSourcesMaintenanceGuard` for a target15 source and open `ReviewStoreMaintenance`. Inside `with_review_maintenance_writer` it must:

1. Call `prepare_egress_backup` with a fresh destination in a separate private backup parent. This uses SQLite's backup API under the retained source writer and verifies schema14, chain, namespace, physical identity and `quick_check` on the real backup.
2. Call `install_egress_format15` with that retained backup proof and a validated `EgressStoreLimitsV1`. The transaction installs empty deny-all genesis, immutable limits and exact15. A failed operation does not yield a committed receipt.
3. Call the writer's explicit `commit`, then reopen and verify the source. The pending install receipt alone is not a committed result or a readiness capability.

Resumption uses `resume_egress_backup`, which reads and verifies the existing backup; it never overwrites or recreates a missing backup. Same migration/prefix/limits returns the retained genesis receipt. Missing/foreign/stale backups, active consumers, unsupported formats and changed limits refuse. Existing source authority cannot be reconstructed from rows, a backup receipt or genesis JSON. This development task migrates only disposable synthetic fixture data.

## Retained limits and terminal capacity

Genesis persists limits, and every reopen replays them. This version has no reconfiguration or deletion path. Defaults are 128 active heads, 16,384 retained entries and 16 MiB serialized snapshots. Hard ceilings are 4,096 heads, 65,536 entries and 64 MiB snapshots. Positive smaller limits are supported and visibly refuse exhaustion. These are logical software bounds, not measurements of 100 workers. The saturation parents reach event-count boundaries and verify serialized-byte/quota agreement; they do not measure physical byte saturation.

The entry invariant is `operations + revisions + active_heads <= retained_entry_limit`. Each active head holds one terminal operation slot, one audit event and 98,304 audit bytes. A replacement transfers that reservation; a revoke consumes only its own exact reservation in the same checked transaction. Every other audit append class, including control and identity maintenance, is admitted against physical capacity less all outstanding egress reservations. The opaque terminal debit is bound to the actual transaction, head, epoch and operation; no event kind or request flag can choose it. Existing human/workload/control/identity budgets remain separate.

An exhausted held egress audit partition has a distinct internal `AuditReservationExhausted` cause. Ordinary/control class budget refusals retain their existing typed cause; sources without an outstanding egress reserve retain their previous physical-capacity errors. This changes no threshold, budget, owner guard or terminal authority.

Closed policy snapshots are at most 65,536 bytes, audit events 98,304 bytes and receipts 4,096 bytes. The accepted core's 128 exact DNS destinations and fixed identifiers establish a preallocation envelope; serialization is checked again and never truncated. Physical SQLite FULL, I/O or commit failure can still prevent revocation. Logical reserves do not preallocate disk and cannot promise availability under storage failure.
