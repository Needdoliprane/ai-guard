## Choix proposé

Conserver `InvocationBindingV1` politique2 pour le programme approuvé et son environnement historique. Ajouter un **profil de commande distinct pour les starts préarmés**, appliqué par `ManagedRuntime` avec `--config <répertoire privé>` avant `start --attach`. Ce flag prime sur DOCKER_CONFIG selon le [CLI au SHA retenu](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/config/config.go#L16-L26).

Le profil minimal v1 contient exactement les octets générés `{}\n` dans `config.json`, sans copie du compte : aucun HttpHeaders, auths, helper configuré, alias, contexte ou plugin importé. La destination moteur reste l'endpoint Unix explicite de l'autorité. Ni profil arbitraire ni chemin ne viennent de Submit/worker. Si un endpoint exige des headers privés, ce profil est incompatible : diagnostic explicite, sans ajout implicite de credential.

Deux alternatives écartées pour ce lot : changer globalement DOCKER_CONFIG ou la politique2 modifierait aussi les usages historiques et les opérations Build/Pull/account ; un transport Rust direct aurait une maîtrise différente des réponses mais dépasse ce prérequis ciblé. Le choix proposé ne modifie ni le Build/Pull existant, ni le login, ni les credentials du compte ; seuls les nouveaux transports préarmés strictement sélectionnés utilisent ce profil. Tous leurs helpers concernés utilisent le même chemin de start.

Attention au fallback Docker : le [chargeur](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/config/config.go#L123-L163) tolère l'absence, ignore certaines erreurs après avertissement et peut détecter un credential-store par défaut. L'absence de header est donc contrôlée par les octets admis côté Rust, pas par un stderr vide ou une absence de fichier. Le profil minimal ne prétend pas désactiver toute détection interne de helper ; le chemin start étudié n'a pas d'opération d'authentification registry à lui confier, à vérifier sur le vrai CLI sélectionné.

## Verticale de données proposée

1. **Sélection explicite en configuration neuve.** Versionner la forme de profil opérateur dans `broker/service/profile.rs` (`RegistryWireV1`, `ControlProfileV1`). Le nouveau mode fixe un profil minimal connu ; les registres anciens restent lus comme historiques, sans réécriture ni qualification D5 implicite. Une configuration neuve documentée sélectionne le nouveau mode. Un job déjà accepté conserve toujours son choix initial, même après modification/restart du registre.
2. **Gel dès Submit accepté.** Dans `runner/broker.rs::PreparedSubmission` et `broker/journal.rs`, ajouter une nouvelle enveloppe de bindings, conservant `BindingManifestV1` None/Manual/Provider intact. Elle engage opération+intent hash, version du profil, ref relative, SHA des octets et fingerprint de l'invocation approuvée ; `Accepted.bindings_hash` engage l'ensemble. Écrire le fichier généré sous le répertoire privé du job neuf, le synchroniser avec ses parents, puis seulement publier Accepted. Sur replay, charger ce binding avant toute préparation ou relecture de choix courant. Aucune dépendance à une source utilisateur ni à son `.docker`.
3. **Capacité vivante et reprise.** Un petit module Rust `runtime/launch_profile.rs` peut porter description sérialisable fermée et handle non sérialisable retenant `Directory`/`PrivateFile`. Réutiliser `control_fs::persistent_create/read/revalidate/sync` : répertoire0700, fichier0600, créations exclusives, taille exacte, liens/ACL/UID/substitution refusés ; aucune réparation d'une entrée existante. Reprise = ouvrir uniquement la ref durable attendue et vérifier les octets/identités ; fichier absent ou divergent interdit une nouvelle émission stricte, sans recréation silencieuse. Pas de nettoyage automatique.
4. **Binding sans casser l'historique.** Ajouter dans `RuntimeAuthority` un `docker_launch_profile: Option<…>` omis quand absent. Il lie description précédente, invocation fingerprint et endpoint. Garder strictement inchangés la sérialisation des anciens None et `RuntimeAuthority::fingerprint()` : ce dernier sert déjà aux Arm/handles et exclut l'invocation. Vérifier séparément égalité binding accepté ↔ autorité ↔ invocation. Le nouveau seed d'autorité doit avoir un namespace/version et une clé engageant la description complète du binding, dont opération/ref du répertoire, version, SHA de config et invocation. Le SHA des seuls octets `{}\n` est constant entre jobs et ne suffit pas : endpoint+invocation+ce SHA pourrait réadopter le seed et la ref du premier job. Ne remplacer aucun seed historique.
5. **Avant effets puis juste avant spawn.** `runner/managed.rs::broker_prepare/broker_runtime`, `AuthenticatedBatchContext` et l'exécuteur font suivre le binding accepté jusqu'au checkpoint managed, avant Admission/Arm/claim. `ManagedRuntime::command()` reste historique pour les opérations non start. Une couture de préparation du seul start préarmé ajoute `--config`, valide et retient la capacité, puis compare en mémoire son identité avec celle attendue par le contrôle préarmé. La garde finale ne reçoit aujourd'hui que le CID : le nouveau profil ne doit pas rester une hypothèse du caller. Conserver la garde consommable adjacente au spawn, sans IO/await ajouté après elle ; aucune nouvelle émission ni annulation automatique du start lors d'un échec/retry.
6. **Enforcer et lecteurs durables.** `RegistrationV1::digest()` sérialise l'autorité complète et engagera le nouveau champ ; son contrôle doit le recouper explicitement. Ajouter aussi l'immutabilité du profil aux validations de checkpoint et du reader STOP : les seuls hashes d'autorité existants ne l'imposent pas. Au replay/restore, ne recréer aucun permis. L'ouverture de base de `ManagedRuntime` et `stop_snapshot_owned` doivent rester utilisables si le fichier du profil a disparu : ce nouveau prérequis de lancement ne doit pas devenir un prérequis d'arrêt. Le reader STOP valide l'engagement de métadonnées mais ne demande ni blob fournisseur ni fichier de profil pour continuer les arrêts déjà armés.

L'intention existante, les plans fournisseurs1/2/3, le hash d'autorité moteur et les claims consommés restent inchangés. Le nouveau lecteur accepte l'ancien format ; un ancien binaire strict doit refuser les nouvelles versions, sans promesse de rollback avec jobs actifs.

## Frontière de « figé » et acceptation

Un digest avant spawn ne garantit pas à lui seul le fichier qu'ouvrira ensuite Docker par pathname. La proposition utilise la frontière actuelle `control_fs` : privé au compte de contrôle, FD retenus, publication immuable par le code coopérant et revalidation immédiatement avant de transmettre le nom (`control_fs.rs:170–184`, `persistent.rs:265–270`). Les courses hostiles du même UID/root sont explicitement hors de cette politique. Ne pas présenter cela comme un scellement OS contre ce compte. Une solution par FD hérité demanderait une preuve distincte macOS/Linux ; aucun `/dev/fd/.../config.json` portable n'est présumé ici.

Le lot est accepté seulement si le parcours réel « nouvelle configuration → Submit → Review éventuel → reprise → start de helper/worker → erreur récupérable » transporte le même binding, refuse ses substitutions et ne modifie aucun fichier/credential historique. L'UI/diagnostic expose nom/version/digest et provenance du profil, avec état absent/invalide/historique ; aucun chemin privé ni contenu de configuration publié. Absence/erreur après claim conserve ce claim consommé et l'inconnue.

Le cas réel Docker reste distinct, sur ressources neuves autorisées, sans fournisseur et sans répéter la matrice entière ; il doit également recouper terminal indépendant et ACK. ## Autorité et limites

C'est un changement interne de l'adaptateur/broker Rust existant : fichiers privés additionnels et formats versionnés dans le journal actuel, sans nouvelle DB/service/identité/secret ni accès worker supplémentaire. Il exige revue de lancement/sécurité, compatibilité et documentation de migration ; la présente proposition ne vaut pas autorisation d'implémentation. Remplacer le transport, introduire proxy/helper permanent, changer la frontière UID/stockage/secret ou les plans existants exigerait une proposition structurelle motivée selon AGENTS.

Ce profil ferme un prérequis de configuration. Il ne prouve ni réponse HTTP normale, ni absence de start en vol, ni complétion de l'emitter exact : aucun constructeur de témoin D5, booléen de succès persistant ou retrait n'en découle. PASS pour cette conception source ; implémentation et tests NOT_RUN ; qualification de ce profil et D5 ouvertes ; G09 FAIL conservé, aucun gate clos.
