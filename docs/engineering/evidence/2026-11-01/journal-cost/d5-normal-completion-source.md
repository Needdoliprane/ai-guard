## Conclusion réfutable

Le Docker CLI étudié n'émet pas son start dans une goroutine indépendante : le chemin attach attend le retour de ContainerStart. Côté Moby étudié, la réponse204 suit le retour du backend, qui attend le démarrage de la tâche. **Un unique POST start dont cette réponse normale exacte a réellement été obtenue est donc un candidat de preuve de fin de requête.** Aucun contre-exemple à cette propriété restreinte n'a été trouvé dans les chemins lus. Cela ne qualifie pas le binaire H10, ne prouve pas l'unicité des transactions HTTP réellement émises et ne rend pas `exit0` ou `ManagedPrearmedExecution Ok` suffisants.

Le CLI est qualifiable en principe sous un profil fermé et attesté ; cette lecture n'établit pas qu'un transport Rust soit intrinsèquement nécessaire. Avec les observables et la configuration actuels, le témoin D5 reste cependant non constructible. Un transport Rust single-shot donnerait une maîtrise directe des transactions/réponses ; il ne dispenserait ni de la preuve serveur, ni du terminal indépendant, ni de son ACK. Aucun changement de transport n'est proposé ici.

## Faits de source et contre-exemples limités

**Ordre CLI.** [start.go:82–169](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/command/container/start.go#L82-L169) inspecte le CID, attache les flux, ouvre wait puis appelle ContainerStart synchroniquement. Après succès de cet appel, il attend l'attach et le statut. Le detach peut retourner nil avant un terminal ; il intervient néanmoins après ce retour de start. Donc detach n'est pas ici un contre-exemple à « aucun start en vol ». La goroutine de signaux appelle kill, pas start ([signals.go:14–53](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/command/container/signals.go#L14-L53)).

**Réponse serveur.** [route:264–287](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/server/router/container/container_routes.go#L264-L287) écrit204 après retour sans erreur du backend. [daemon/start.go:90–252](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/start.go#L90-L252) tient le verrou du conteneur et attend `tsk.Start`, puis met Running avant retour. Les opérations NewTask/Start emploient un contexte non annulable : une perte de connexion n'annule donc pas nécessairement le démarrage. Inférence : réponse normale exacte obtenue pour une transaction unique ferme cette invocation du handler ; timeout, annulation et réponse perdue ne la ferment pas par observation du client. Aucune panne ni sémantique réelle containerd n'a été testée ici.

**POST et réponse perdue.** Le [client ContainerStart](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/vendor/github.com/moby/moby/client/container_start.go#L18-L36) fait un POST synchrone. [request.go:97–121,198–204](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/vendor/github.com/moby/moby/client/request.go#L97-L121) n'ajoute pas de boucle de retry métier ; il délègue à HTTP et accepte les statuts200–399. Il ne transmet pas au parent un reçu204 typé. Le [client HTTP par défaut](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/vendor/github.com/moby/moby/client/client.go#L126-L147) refuse les redirections POST. L'API officielle [v1.53](https://docs.docker.com/reference/api/engine/version/v1.53/) documente204 et304 pour start, pas202 ; accepter un autre statut ne démontre pas à lui seul une réponse conforme du moteur choisi.

**Retry conditionnel concret.** [Go Transport:751–795](https://github.com/golang/go/blob/69801b25b9624c3a678ef87d30771861e7bba51f/src/net/http/transport.go#L751-L795) peut réessayer après zéro octet écrit sur connexion réutilisée : cela ne crée pas un premier start livré. Après une erreur de lecture de réponse, le retry exige une requête rejouable. [Request:1441–1454](https://github.com/golang/go/blob/69801b25b9624c3a678ef87d30771861e7bba51f/src/net/http/request.go#L1441-L1454) traite un POST sans corps portant Idempotency-Key ou X-Idempotency-Key comme rejouable. Cette propriété ne signifie pas que le moteur déduplique ces start.

Le CLI charge les [HttpHeaders de config:281–297](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/command/cli.go#L281-L297), ensuite appliqués aux requêtes par [request.go:283–291](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/vendor/github.com/moby/moby/client/request.go#L283-L291). Dans ai-guard, `Runtime::command` nettoie l'environnement (`runtime.rs:659–668`), mais `standard_environment` fixe DOCKER_CONFIG au `.docker` du compte de contrôle (`invocation.rs:568–583`). `--host` fige la destination (`managed.rs:497–518`), pas le contenu de config.json ; l'identité d'invocation ne hash pas ce contenu. Aucun fichier réel n'a été lu. **Écart de preuve**, pas incident observé : une configuration portant une clé d'idempotence peut autoriser un deuxième POST après une réponse perdue. Avec un premier envoi encore retenu par un relais puis livré tardivement, la réponse du retry ne prouverait pas sa disparition. Cette intercalation reste NOT_RUN ; elle ne doit pas être affirmée pour H10.

**Wait/cancel et codes.** [ContainerWait](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/vendor/github.com/moby/moby/client/container_wait.go#L24-L84) attend les headers avant de rendre ses canaux. [waitExitOrRemoved:24–43](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/command/container/utils.go#L24-L43) ferme son canal sans statut lors d'une annulation ; une lecture sans test d'ouverture obtient alors zéro. Le CLI mélange aussi statut métier nonzero et erreurs d'attach/wait. Ces faits invalident une définition trop large de « fin normale », mais n'établissent pas un start encore en vol : ces branches de fin suivent déjà l'appel synchrone. Un stderr vide ou un code égal au terminal ne transforme pas ce mélange en résultat typé.

**Descendants.** [connhelper](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/connhelper/connhelper.go#L38-L59) peut lancer SSH ; [commandconn:32–69](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cli/connhelper/commandconn/commandconn.go#L32-L69) détache sa durée de vie du contexte appelant. Cela interdit une conclusion générale fondée sur le seul reap du PID CLI. Ce n'est pas un descendant démontré pour le profil Unix direct. Le start builtin n'est pas remplaçable par un alias start dans cette version ([aliases:16–27](https://github.com/docker/cli/blob/a5c7197d720daef7d8b9e6174ee78c0743cea166/cmd/docker/aliases.go#L16-L27)).

## Ce que l'objet ai-guard actuel prouve

`execute_created_prearmed` consomme la garde, spawn un unique child possédé, attend son statut, contrôle StartedAt/terminal et clôture les pipes (`runtime.rs:1086–1288`). Il accepte un statut nonzero ; son chemin d'erreur/notification conserve l'inconnue. `ManagedRuntime::execute_owned` relit ensuite le terminal exact (`managed.rs:1093–1161`). `ManagedPrearmedExecution::from_retained` ne conserve que capture, code transport et durée avec snapshots (`:153–190`). Il ne garde aucun reçu de fin HTTP ni binding claim/emitter/epoch/génération. Les types présents sont ExecutionResult/PrearmedExecutionResult ; aucun CapturedProcess n'a été trouvé dans les deux fichiers demandés. Le terminal et l'ACK central ne reconstruisent pas la provenance perdue de l'émetteur.

## Conditions fermées avant un témoin vivant éventuel

Il faudrait établir ensemble : binaire et dépendances exacts ; profil de transport/configuration fixé sans retry ambigu ni émetteur auxiliaire ; unique émission fraîche liée Arm/digest/claim/emitter/epoch/génération/CID/autorité ; branche de complétion réellement normale avec réponse moteur conforme et aucune transaction émise encore inconnue ; puis terminal indépendant du même snapshot et ACK central vérifié. Perte de réponse, arrêt forcé, annulation non classée, redémarrage ou perte d'une de ces preuves doit refuser le témoin. Un nonzero métier peut être normal seulement si sa provenance est distinguée de l'erreur transport ; le code seul ne le distingue pas.

C'est une liste de conditions de preuve, pas un protocole de retrait ni un nouveau constructeur. Les sources permettent de travailler une qualification CLI ciblée ; elles ne suffisent pas à décider que ces conditions sont satisfaites. Aucun booléen durable, absence de CID ou terminal historique ne remplace un témoin vivant, et aucun témoin ne peut être recréé rétrospectivement pour les anciens slots depuis cette note.
