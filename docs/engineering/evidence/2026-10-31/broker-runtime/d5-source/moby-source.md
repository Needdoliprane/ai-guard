**Verrou commun.** Container incorpore State ; le mutex de State protège les deux. La fonction qui pose RemovalInProgress acquiert ce mutex, et celle qui le réinitialise le reprend. Le drapeau de retrait n'est pas sérialisé sur disque ; Dead l'est. C'est une coordination locale du daemon, pas un verrou durable partagé avec un client. [State au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/container/state.go), [Container au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/container/container.go).

**Start.** ContainerStart résout d'abord l'identifiant, vérifie l'état, puis containerStart reprend le mutex et recontrôle les états de retrait/mort. Ce verrou reste tenu pendant la préparation, la création de tâche et son démarrage ; des opérations de tâche utilisent un contexte non annulable. Une déconnexion du demandeur ne démontre donc pas l'annulation de l'effet. Le retour anticipé pour une instance déjà Running n'émet pas de nouveau démarrage. [start.go au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/start.go).

**Retrait.** containerRm pose RemovalInProgress avant le nettoyage et le réinitialise en sortie. cleanupContainer refuse une instance active sans ForceRemove ; il tente ensuite l'arrêt, marque Dead sous verrou, tente de persister cet état, enlève le répertoire puis désinscrit l'objet. Un échec du checkpoint Dead est journalisé sans interrompre automatiquement le retrait. Les échecs intermédiaires ne sont donc pas équivalents à un retrait terminé. [delete.go au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/delete.go).

**Courses — inférences conditionnelles, pas garanties.** Si le même objet a déjà été résolu mais que le start attend le verrou, un retrait ayant réellement atteint Dead laisse ce marqueur sur le pointeur ancien ; le recontrôle du start devrait empêcher une nouvelle émission. Si le start détient déjà le verrou, le retrait attend son passage : sans force, il peut ensuite refuser l'instance devenue active. Un start bloqué peut donc empêcher le retrait de progresser ; aucun délai de fencing n'est établi par cette lecture. Ces inférences combinent les verrous et contrôles précédents ; elles ne démontrent ni les intercalages réels ni le résultat des appels containerd.

**Avant lookup : le CID complet n'est pas un type strict.** GetContainer cherche d'abord l'ID exact, puis un nom exact et enfin un préfixe. Après disparition de l'ID original, une requête retardée portant ses64caractères peut donc résoudre un autre objet nommé avec cette chaîne. Ce comportement concerne aussi un nouvel appel remove. Une observation ou validation d'identité réalisée avant l'ancien start ne fige pas cette résolution ultérieure. [daemon/container.go au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/container.go).

Cette collision de nom est un contre-exemple possible dans la source : la réservation valide longueur/caractères, et le motif accepte une chaîne hexadécimale64caractères ; aucune exclusion des noms ressemblant à un CID n'apparaît dans ces fonctions. Sa réalisation sur le build observé est NOT_RUN. Une clôture D5 couvrant les requêtes encore avant lookup doit établir une exclusion effective de cette réutilisation, ou employer une autre primitive démontrée. [Réservation des noms au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/names.go), [motif des noms au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/names/names.go).

**Réponse remove, absence et timeout.** Le routeur retourne204 après succès du backend remove ; il ne remet pas un reçu de fencing causal lié à l'ancien start. Une absence préalable n'atteste aucun retrait, et une réponse perdue ne révèle pas le point atteint. Le backend remove n'est pas annulé à partir du contexte HTTP transmis à la route. Pour ai-guard, un timeout ou une observation d'absence doit donc rester une issue inconnue tant que sa propre preuve exacte n'existe pas. [Routes au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/server/router/container/container_routes.go).

**Redémarrage daemon.** Le démarrage relit les répertoires et leurs métadonnées, recoupe l'état des tâches et applique une logique de restauration/redémarrage. Il contient un traitement de RemovalInProgress hérité que son commentaire signale comme probablement redondant depuis la non-persistance du drapeau. Des objets Dead peuvent faire l'objet d'un nettoyage. Le verrou mémoire de l'ancien processus n'est plus une preuve ; restaurer un backup ou changer de data-root n'entre pas dans une continuité démontrée. La survie de tâches via live-restore impose aussi de distinguer mort du daemon et mort de la tâche. [daemon.go au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/daemon.go).

**Panne électrique et persistance.** CheckpointTo passe par toDisk puis une sauvegarde de la vue. Dans les fonctions lues, toDisk diffère Close sans utiliser son erreur ; le writer peut échouer pendant cette fermeture. [Container/checkpoint au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/container/container.go).

Le writer vendorié synchronise le fichier puis ferme, change le mode et renomme ; aucun sync du répertoire parent n'apparaît dans ce Close. [atomicwriter au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/vendor/github.com/moby/sys/atomicwriter/atomicwriter.go). Le helper de suppression appelle RemoveAll et gère certaines erreurs/reprises, sans barrière de répertoire explicite dans ce fichier. [containerfs/rm.go au SHA](https://github.com/moby/moby/blob/0367cbeb49b9d98cb0b4f51e95f7b54b4803e76c/daemon/internal/containerfs/rm.go). Ces lectures ne prouvent aucune résurrection ; elles interdisent simplement de déduire une garantie powerloss d'un retour remove ou d'un commentaire d'intention.

**Conditions qu'une éventuelle preuve ai-guard devrait établir.** Conserver une intention de fencing autorisée/auditée, l'Arm et l'ancien claim consommés, les preuves de terminal/copie nécessaires avant toute suppression, l'autorité moteur immuable et le vrai CID. Exiger un résultat vérifié de la primitive, lié à cette cible, puis un ACK durable de retrait idempotent ; un refus, timeout, origine changée ou preuve perdue retient le slot. La non-réutilisation par nom, les autres installations autorisées sur ce moteur et la continuité après restart doivent être dans le périmètre prouvé. Cette note ne choisit ni n'implémente une telle primitive et n'autorise aucune suppression.
