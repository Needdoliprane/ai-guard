## Comportement livré

- `Directory` cloneable : ouverture ou création par `openat`/`mkdirat` depuis `/`, `O_NOFOLLOW|O_DIRECTORY|O_NONBLOCK|O_CLOEXEC` à chaque composant, contrôle de chaque propriétaire/mode/ACL, racine privée euid/0700. Les ancêtres appartiennent à root/euid sans écriture groupe/autres ; seule l'exception root/sticky est admise, et chaque enfant reste contrôlé root/euid et protégé selon sa propre politique. Aucune exception pour le groupe admin.
- `PrivateFile` cloneable : source ou enfant ouvert par FD, régulier, euid/0600, nlink=1, lecture `NONBLOCK` bornée avant consommation, vérification des métadonnées avant/après ; bytes et SHA-256 sont conservés sans réouverture de pathname. Borne demandée par l'appelant avec plafond global de 32 MiB, compatible avec la limite des checkpoints existants.
- `Snapshot` cloneable : création exclusive en 0600 sous une Directory retenue, bytes/digest calculés directement sur l'entrée préparée, pas de TMPDIR ambiant. `private_file()` partage la même durée de vie et le cleanup au dernier handle, utile pour ContainerSpec.
- `revalidate()` vérifie à nouveau la politique et l'identité de toute la chaîne de répertoires ; les fichiers comparent également l'état du FD préparé et de l'entrée courante. `path()` est une provenance et demande cette revalidation avant handoff CLI.
- Nettoyage seulement pour les snapshots nouvellement créés, par `fstatat(AT_SYMLINK_NOFOLLOW)` puis `unlinkat` relatif au FD parent retenu avec identité dev/inode/type/nlink. Les remplaçants observés sont conservés ; un parent renommé ne redirige pas le cleanup. Les fichiers source et les répertoires existants ne sont ni chmodés, ni déplacés, ni supprimés.
- Debug opaque pour tous les handles ; aucun FD sérialisé et aucun contenu, digest ou pathname dans Debug.
- `absolute_path` : current_dir pour un relatif, normalisation lexicale de `.`, refus de `..`, aucun suivi de symlink arbitraire. Seulement sous Darwin : traduction par composants des trois alias OS `/var`, `/tmp`, `/etc` vers `/private/...`, dont la cible reste inspectée par FD.

## Politique plateforme et limites

Darwin : inspection FD des ACL via API native, comparaison des signatures et constantes au SDK local. Toute ACL étendue de feuille privée est refusée, y compris deny. Les ancêtres admettent les ACE deny et les ACE allow de lecture/recherche seulement ; toute ACE allow de mutation est refusée conservativement, même si elle désigne root/euid. Les ACL préexistantes ne sont jamais retirées. Le contrôle filesystem refuse désormais aussi le flag `MNT_IGNORE_OWNERSHIP`/`MNT_UNKNOWNPERMISSIONS` (voir l'addendum FS-1).

Linux : le code s'appuie sur le masque POSIX ACL exposé dans les bits groupe. Les types pris en charge par la politique sont ext*, XFS, Btrfs, tmpfs, overlayfs, ramfs et F2FS. Darwin exige APFS/HFS avec MNT_LOCAL. Ces allowlists ne constituent pas une qualification de chaque filesystem, et NFS/SMB/FUSE restent refusés. La racine exécutée ici est APFS ; HFS et tous les types Linux restent NOT_RUN.

Les processus du même UID, root, les administrateurs moteur/stockage et les changements de mounts privilégiés sont hors garantie DAC. Le couple contrôle d'identité/unlink n'est pas une primitive atomique contre un writer du même UID ; la sûreté autre UID repose sur les parents privés/sticky contrôlés. Le cleanup Drop est best effort ; un échec peut laisser un snapshot pour diagnostic. Ce module ne qualifie pas la réouverture SQLite/VFS/WAL, les CLI Docker/Podman, ni les parcours callers du lot suivant.

## Addendum FS-1 et handles internes, après revue

**Cause constatée et RED** : le validateur Darwin initial acceptait un type APFS/HFS local sans examiner le flag qui ignore l'ownership. Le [SDK local sys/mount.h:229](/Library/Developer/CommandLineTools/SDKs/MacOSX27.0.sdk/usr/include/sys/mount.h:229) définit `MNT_IGNORE_OWNERSHIP=0x00200000`, avec l'alias [MNT_UNKNOWNPERMISSIONS:241](/Library/Developer/CommandLineTools/SDKs/MacOSX27.0.sdk/usr/include/sys/mount.h:241). Un test du validateur extrait sans changement de comportement initial a effectivement échoué pour `MNT_LOCAL|0x00200000` sur les deux types. Aucun volume n'a été remonté et aucune action root n'a été faite.

**Correctif** : `validate_filesystem_permissions(&File)` est une fonction interne partagée, fail closed. Toute inspection des répertoires/fichiers de contrôle refuse ce flag ; `identify_directory` et `identify` d'invocation l'exigent aussi sur le FD de répertoire terminal et sur le FD du programme, avant de faire confiance aux observations UID/mode. Aucun contrat sérialisé, version de policy, schéma ou mécanisme de fencing ajouté. Une comparaison source contre l'archive 261 constate exactement deux lignes ajoutées dans invocation ; cette archive historique ne qualifie pas ce nouveau code.

**Impact Linux** : les types pris en charge par la primitive restent inchangés, mais l'exigence est désormais appliquée aussi aux programmes runtime et à leurs répertoires terminaux. Les exécutables sur ext*, XFS, Btrfs, tmpfs, overlayfs, ramfs ou F2FS passent ce filtre de type ; ZFS et tout autre type non listé, NFS/SMB/FUSE notamment, sont refusés. Aucun effet Linux n'a été exécuté ici ; un type autorisé reste une politique de support, pas une qualification de plateforme.

**API interne pour les callers** : `Directory::try_clone_file()` revalide puis clone le FD déjà retenu, sans réouverture par pathname. Les tests conservent son identité/lifetime après drop du handle, exigent CLOEXEC et refusent le clone si le pathname de la Directory a changé. `PrivateFile::is_within_directory(&Path)` revalide la source puis compare l'identité dev/inode du projet à sa chaîne d'ancêtres retenue. Le lookup du projet n'exige pas la politique DAC privée du contrôle : un projet 0755 ou 0777 peut être inspecté, et les alias de casse/Unicode représentent le même objet filesystem. Un projet manquant ou non inspectable renvoie `Err`, jamais `false` ; la politique de reprise depuis une archive immuable appartient au caller. Cette API n'est ni une autorisation ni une API exposée aux workers.

**RED/GREEN constatés** : `cargo test --locked --lib control_fs::descriptor_tests` a d'abord produit 2 échecs attendus (noowners accepté et clone non implémenté), puis 3 PASS après correctif ; le test de containment ajouté ensuite a échoué sur le stub avant implémentation. Dernière exécution avec les assertions RootMissing/lookup projet 0777/CLOEXEC : **4 PASS, 0 échec, 0 ignoré**.

**Autres vérifications constatées après FS-1** : `cargo test --locked --test control_fs --test runtime_program` → **15 + 8 PASS**, zéro échec/ignoré. Une warning dead_code du clone au moment où le caller ne l'avait pas encore intégré était visible pendant cet essai ; les appels existent maintenant dans les wrappers du caller. Dernier `cargo clippy --locked --lib --test control_fs --test runtime_program -- -D warnings` → **PASS** après ajout du containment et intégration des callers. `rustfmt --edition 2024 --check src/control_fs.rs src/runtime/invocation.rs tests/control_fs.rs` → **PASS**. Les premiers essais clippy de ce complément ont signalé deux imports OpenOptionsExt devenus inutiles dans les fichiers du caller ; son lot les a retirés avant la validation finale.

**Revue indépendante complémentaire** : `/root/trusted_runtime_core/invocation_review` a relu le rejet noowners, les deux appels FD d'invocation, le clone du FD retenu et le lookup d'identité containment : aucun défaut concret supplémentaire identifié. Le test pur des flags n'est pas une preuve runtime du montage.
