# Revue lecture seule — README et quick start

Date : 30 octobre 2026. Revue documentaire indépendante, sans build, stack, Docker, tests E2E ni appel fournisseur. Référence CLI : /tmp/ai-guard-sqlite-freeze.DezAml/agentsandbox (version agentsandbox 0.1.0, gel SQLite 327). Sémantique recoupée avec sources Rust et l’essai Codex réel autorisé précédemment.

## Constats à corriger avant intégration

1. **README écrit par défaut les clés sous le checkout — priorité haute.** README.md:47,58-60,90,92 annonce que ses exemples emploient .agentsandbox par défaut, puis fait init depuis la racine du dépôt. Cela met secrets et état privé dans le checkout, contrairement au Quick start (docs/quickstart.md:30) qui exige une configuration extérieure au checkout et au projet, ainsi qu’aux instructions de travail du dépôt. Même si le nom est ignoré par Git, ce n’est pas le bon choix par défaut pour un guide destiné aux nouveaux utilisateurs. Recommander AIGUARD_CONFIG="$HOME/.ai-guard" et passer --config-dir aux commandes qui le prennent; préciser séparément que doctor et build n’ont pas ce flag. Ou, si les exemples courts gardent .agentsandbox, avertir clairement de son emplacement et des risques, sans le présenter comme parcours recommandé.

2. **L’exemple Codex du Quick start ne reproduit pas l’essai cité et l’étape d’export vérifie un autre nom.** docs/quickstart.md:189-199 demande result.txt avec le contenu « Essai ai-guard. », tandis que le second essai réel réussi a demandé le contenu exact « Codex local smoke test completed. ». L’étape 6 (:107,125) vérifie ai-guard-example.txt et ne peut donc pas être suivie telle quelle après ce run. Remplacer le prompt par celui de l’essai réussi, puis ajouter une courte vérification d’export pour result.txt (ou dire précisément quels noms remplacer à l’étape 6). L’essai réel utilisé --model gpt-6-luna, --sandbox danger-full-access, --skip-git-repo-check, --ephemeral, -c 'approval_policy="never"', timeout 300, profil observe/réseau bridge et le fichier credentials via --secret-env-file. Le premier essai workspace-write s’est terminé exit 0 mais n’a créé aucun fichier : bwrap n’a pas pu créer un namespace utilisateur. Le texte signale déjà cet échec (:202) et utilise les bons flags du second essai; c’est le prompt/critère qui doit être aligné.

3. **L’exemple fournisseur README n’est pas une recette création/export.** README.md:157-168 demande seulement de décrire la structure du projet, puis le texte adjacent dit que l’essai réel a produit un fichier et un export. Ce n’est pas un faux résultat affirmé de cette commande, mais l’exemple ne permet pas de reproduire la preuve de fichier que le paragraphe décrit. Employer le prompt minimal exact du second essai et ajouter les étapes d’export/contrôle du résultat, ou identifier explicitement cet exemple comme exploration sans fichier et lier la recette vérifiable du Quick start.

4. **Le flag de programme moteur personnalisé n’est pas propagé dans le parcours documenté.** docs/quickstart.md:45 indique qu’une installation peut demander --runtime-program, mais seulement dans l’exemple de doctor. Le chemin est une option par invocation, pas une configuration persistante : build, up, run, down, worker-stop/resume et export-workspace disposent chacun de leur forme correspondante. Un utilisateur chez qui seul doctor --runtime-program ... réussit peut ensuite voir les autres commandes résoudre un autre programme. Préciser de répéter le flag là où l’aide le propose, éventuellement lister les sous-commandes visées et leurs limites. Même point à signaler dans le dépannage si le lecteur choisit un exécutable non standard.

5. **Guillemets absents sur les chemins de remplacement.** docs/quickstart.md:26,113-114 montre les assignations AIGUARD_PROJECT=/... et AIGUARD_EXPORT=/... sans guillemets. Elles cassent si un chemin contient des espaces. Écrire AIGUARD_PROJECT="/chemin/...", AIGUARD_SESSION="UUID...", AIGUARD_EXPORT="/chemin/..."; README utilise également des arguments de projet non cités (README.md:101-106, etc.) et devrait citer ses chemins si les exemples prétendent accepter des espaces.

## Vérifications et faits confirmés

- **PASS — aide CLI.** doctor, build, up, down, run, init, export-workspace, worker-status, worker-stop, worker-resume, verify-audit : options documentées disponibles sur le binaire gelé. Détails utiles : doctor/build n’acceptent pas --config-dir; down n’accepte pas --allow-rootful-runtime; l’export et les commandes worker ne prennent pas --runtime et utilisent la session/registre; worker-status ne reçoit pas --runtime-program, mais stop/resume en ont une option dédiée. Timeout resume = --wait-seconds (30 par défaut).
- **PASS — Docker/Podman et ports.** Les profils de runtime, choix d’un seul Compose, ports loopback 4000/8787 et propagation de --allow-rootful-runtime à doctor, build, up, run sont cohérents avec l’aide/source. L’absence du flag sur down est explicitement dite dans le Quick start. Podman rootless est bien assorti d’un fournisseur podman compose.
- **PASS — profils, réseau et credentials.** runner.rs exige observe pour bridge et observe + bridge pour --secret-env-file; le réseau par défaut reste none. Les descriptions strict/review/observe, interdictions explicites, hash complet d’approbation et risque de commandes transitives correspondent à policy.rs/runner.rs. runtime.rs ferme stdin métier (Stdio::null()); l’absence de TTY, OAuth hôte ou login interactif est correctement annoncée.
- **PASS — permissions, init, build/up, export et reprise.** L’aide et operations.rs confirment la création de configuration privée, la préservation des clés existantes, les images worker/control, la recréation des services par up, l’export dans une nouvelle destination et l’utilisation des options enregistrées. worker-status lit l’état durable; stop persiste un intent; resume réconcilie sans rejouer un droit de démarrage consommé. Le guide prévient du redémarrage par up et des limites de reprise après mort brutale.
- **PASS — statuts fournisseur.** Codex CLI 0.165.0 a une preuve réelle ciblée de création de fichier et export vérifié dans le rapport associé; Claude Code 2.1.140 a seulement passé version/help, authentification et appel restent NOT_RUN. Le texte n’affirme pas une qualification TUI ou un contrôle des effets transitifs.
- **PASS — liens examinés.** Les cibles locales visées existent et les ancres operations (programme-et-cible-du-moteur, consulter-arrêter-et-reprendre-un-worker, agents-cloud-et-clés-dapi) ainsi que le lien README vers ajouter-un-agent-fournisseur correspondent aux titres. La politique default.json autorise exactement /usr/bin/id; /bin/echo exemple-non-autorise est hors allowlist. Les ports et limites évoqués sont documentés comme paramètres/observations, pas comme preuves de consommation.
- **Durée débutant.** Le Quick start n’annonce pas « 10 minutes », ce qui est préférable : compilation Release, pull des images et dépendances réseau rendent le délai variable. Le parcours local principal est assez concret pour être suivi, sous réserve du correctif de chemins; l’agent fournisseur est facultatif et clairement plus risqué.
