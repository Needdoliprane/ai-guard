## Contrat pratique proposé pour le programme moteur — à valider par root

1. **Choix par le contrôle, une fois.** La configuration privée du broker nomme un programme absolu pour chaque adaptateur. Sa provenance est le contrôle/installateur de confiance ; jamais le projet, le worker ou une requête tenant. Une aide à l'installation peut proposer des candidats, mais ne doit pas exécuter le premier fichier d'un PATH ambiant pour le « vérifier ». Aucun point d'effet, y compris doctor initial, context inspect, image inspect/bootstrap Podman, build, compose, import, run, export, stop, cleanup ou reprise, ne recherche un basename implicitement.

2. **Approbation de l'emplacement et du fichier.** Résoudre une éventuelle chaîne de symlinks depuis un emplacement explicitement approuvé, puis exiger un fichier régulier exécutable et son chemin canonique absolu hors de tout arbre projet/workspace/import/export. Vérifier les propriétaires, modes et ACL pertinents du fichier et de ses parents : aucune écriture par le projet, le worker ou un autre principal non approuvé. La canonicalisation seule ne donne aucune confiance et ne ferme pas une substitution ultérieure d'un parent. Les installations privées de l'opérateur peuvent être approuvées ; exiger systématiquement root comme propriétaire casserait inutilement ce modèle de confiance local.

3. **Pin durable dans l'autorité.** Ajouter à l'autorité privée une version de politique d'invocation, le chemin canonique approuvé, une identité de fichier/contenu contrôlée et les sélections/cwd approuvés. Inclure cette liaison dans le fingerprint de l'autorité. Réouverture et chaque opération utilisent cette liaison ; aucune nouvelle recherche PATH. Un chemin, contenu, propriétaire ou règle de sélection divergent produit un diagnostic et une observation inconnue pour les effets en cours, jamais adoption automatique d'un autre exécutable ni second start. Une mise à jour du CLI est une opération de contrôle explicite avec stratégie pour les sessions actives. Un hash consigne une identité ; il ne remplace pas l'approbation de sa provenance.

4. **Environnement reconstruit.** Construire la commande avec `env_clear`, puis une allowlist propre à Docker/Podman, remplie depuis des valeurs contrôlées et conservées. Conserver explicitement les besoins vérifiés, par exemple langue, HOME/config de contrôle et répertoires XDG/connexion nécessaires. Le PATH éventuellement requis pour les helpers/plugins contient seulement des répertoires absolus approuvés, sans segment vide, relatif ou projet. Le programme principal reste absolu. Toute variable de loader, runtime, plugin ou configuration non approuvée reste absente. Ne pas recopier l'environnement entier avant de retirer quelques sélecteurs. Les valeurs privées de configuration ne vont ni dans les DTO publics ni dans les erreurs brutes.

5. **cwd fixé hors projet.** Utiliser un répertoire de contrôle privé vérifié, par exemple une racine broker dédiée 0700. Tous les chemins fonctionnels (projet source, contexte de build, Compose, env-file, archive) sont passés explicitement en absolu. Ne pas déplacer le cwd vers le projet pour rendre le moteur accessible. Vérifier les effets de ce choix sur Compose, ses plugins, les configs locales et les providers avant acceptation.

6. **Conserver les plateformes demandées.** Le contrat accepte des emplacements approuvés propres à Docker Desktop et aux installations Homebrew/macOS, ainsi que Docker/Podman Linux. Les symlinks d'installation sont approuvés vers leur cible, au lieu d'être tous interdits ou tous crus. Docker garde son endpoint Unix et son engine ID ; Podman garde le mode natif local et le mode remote par socket Unix déjà admis pour VM locale. Une connexion SSH/TCP n'est pas introduite par ce lot. Les helpers/plugins et chemins de configuration utiles sont inventoriés pour chaque version qualifiée ; aucune allowlist minimaliste supposée ne doit fermer artificiellement une plateforme obligatoire. **Ce sont des critères de compatibilité à tester, pas une qualification déjà acquise.**

7. **Fixtures Rust explicites.** Les tests actuels compilent un petit moteur Rust et remplacent PATH. Les faire passer par un chemin absolu de fixture approuvé dans leur configuration privée dédiée, avec cwd/env de test explicitement construits. Une injection de dépendance/commande au niveau bibliothèque peut servir aux scénarios unitaires. Pour les tests CLI, utiliser le même contrat de configuration de contrôle, sans flag de contournement accessible à un worker et sans exemption générale « si environnement de test ». Le protocole de la fixture peut utiliser arguments, fichiers privés ou quelques variables explicitement injectées par le harness ; aucune variable arbitraire de l'hôte n'est nécessaire. Ne pas durcir uniquement ManagedRuntime en conservant des appels legacy non liés avant son initialisation.
