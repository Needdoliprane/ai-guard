# SSO OIDC : contrat et qualification

Constats fonctionnels actualisés le 2 novembre 2026. Le [contrat produit canonique — identité, SSO et configuration](../sso.md) fixe les exigences du mainteneur. Ce document en est la déclinaison technique : il précise les mécanismes, refus et preuves sans réduire la traçabilité individuelle, le mode local nominatif, les points de contrôle signés ou la découverte demandés. En cas d'écart, le contrat produit et AGENTS.md font autorité. Cet alignement documentaire ne requalifie pas le code et conserve les preuves historiques dans leur périmètre daté.

Le SSO est facultatif à l'installation, mais son support et sa qualification font partie du produit demandé. ai-guard est un client OpenID Connect d'un fournisseur configurable, dont Keycloak ; il ne devient pas fournisseur d'identité. Cette déclinaison conserve les frontières du [contrat d'architecture](ARCHITECTURE_CONTRACT.md) et de l'[isolation par tenant](CLOUD_TENANCY.md).

Les [axes de configuration indépendants](../sso.md#configuration-par-axes-indépendants) et le [profil d'inférence interne](../sso.md#inférence-interne-et-déploiement-sans-internet) suivent le contrat canonique : topologie, identité, périmètres/permissions, client et authentification IA, réseau/TLS et exploitation ne sont pas couplés arbitrairement. Le client construit et distribue ses images depuis les Dockerfiles ; aucune image publique préconstruite n'est obligatoire. Ces exigences restent à implémenter et qualifier, sans repli cloud ni garantie pour une combinaison non testée. La connexion SSO ne configure pas les credentials ou l'inférence de Codex/Claude.

**OIDC/PKCE Web/CLI et sa configuration sont implémentés comme candidat ; leur qualification réelle reste ouverte.** Cinq tests gateway à issuer contrôlé, dix-huit tests du ledger initial et quatorze tests CLI humains locaux ont passé sur leurs gels respectifs. Les nouveaux correctifs issus des revues sont en validation ; ces résultats antérieurs ne leur sont pas transférés. Un P2 de nettoyage de préparation reste ouvert. Les [guides opérateur EN](../setup/sso/README.md)/[FR](../setup/sso/README.fr.md) décrivent les fichiers et commandes acceptés. Keycloak réel, navigateur, raccordement Compose complet et bootstrap automatique restent NOT_RUN ou à livrer selon leur périmètre ; aucun gate n'est fermé.

L'accès humain local nominatif est implémenté : provisioning, memberships/grants, API/CLI et dashboard distinct du viewer, avec audit des lectures. Le parcours Docker A/B API/CLI, export, redémarrage et révocation hors ligne passe sur l'image `954246…` issue de `7afdd43` ; le navigateur contre ce contrôle reste NOT_RUN. Les [gels logiciels historiques](VALIDATION.md#1er-novembre--accès-humain-local-apicli-et-dashboard) et les [résultats datés](VALIDATION.md) conservent leurs limites ; cette recette locale ne qualifie ni SSO, ni lancement délégué, ni audit signé complet.

## Connexion Web et CLI

Le contrat cible utilise Authorization Code avec **PKCE S256**, avec deux clients publics distincts pour le Web et la CLI. Aucun `client_secret` n'est distribué dans le frontend, le binaire CLI ou leurs configurations. Les flux implicite et mot de passe sont désactivés ; un échec ne change ni flux ni identité. PKCE lie l'échange du code au vérificateur privé de la transaction. Références : [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html) et [OAuth Security BCP, sections 2.1 et 2.4](https://www.rfc-editor.org/rfc/rfc9700.html).

Chaque connexion possède `state`, `nonce` et vérificateur aléatoires, privés, bornés et expirables. Ils sont liés au client, à l'issuer et au redirect attendus ; leur consommation est unique, y compris après erreur ou deux callbacks concurrents. Refuser callback non sollicité, doublon, transaction expirée, mauvais `state`, mauvais `nonce`, code ou vérificateur rejoué. Valider aussi l'ID token utilisé pour établir la connexion selon [OIDC Core, section 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation). Un ID token ne sert jamais de bearer pour l'API métier.

Les redirects et origines autorisés sont exacts, sans joker ou redirection ouverte. Le gateway est le propriétaire Web approuvé de la transaction, du callback et de l'échange, via le proxy dashboard limité décrit ci-dessous. Le lot doit prouver la continuité au retour du navigateur, la conservation privée puis la consommation des paramètres : une variable mémoire perdue lors d'un rechargement n'est pas une solution. Cette décision ne crée ni BFF ni session métier permanente par cookie ; tout autre changement de frontière ou de stockage exige une proposition motivée avant réalisation.

Pour la CLI, la cible est un navigateur externe et un callback loopback éphémère lié uniquement à une adresse IP loopback, avec chemin fixé et fermeture du listener après une issue corrélée, annulation, échéance initiale ou épuisement du budget de connexions. L'exception de port variable des redirects loopback doit être testée avec le fournisseur ; elle n'autorise aucun joker de chemin ou d'hôte. Voir [RFC 8252, sections 7.3 et 8.3](https://www.rfc-editor.org/rfc/rfc8252.html). Le mode sans navigateur est une capacité distincte, **ABSENTE / NOT_RUN** : ne pas proposer un flux mot de passe, une copie de token ou un flux device supposé disponible comme repli implicite.

Le listener CLI traite au plus huit connexions successives, une à la fois. Un callback malformé, dupliqué ou non corrélé reçoit une réponse locale fixe 400 sans consommer la transaction PKCE ; le même login peut encore recevoir son callback exact. Un code ou refus valide avec le `state` attendu termine cette unique réception ; le code reste soumis aux vérifications complètes du fournisseur. Lecture de chaque pair limitée à deux secondes, écriture et fermeture de sa réponse à une seconde, toujours tronquées par la même échéance monotone initiale couvrant découverte, navigateur et échange. Aucun pair ne renouvelle cette échéance. Ce plafond est une résilience bornée, pas une protection complète contre la saturation locale ; après épuisement ou expiration, une nouvelle connexion explicite est nécessaire.

L'identité humaine CLI demande une action au contrôle avec ses permissions explicites et son attribution d'audit. Le broker garde son identité de workload indépendante. Aucun échange silencieux du token humain contre une clé `runner`, aucune promotion automatique humain → `runner`, et aucun credential d'identité humaine ai-guard dans un worker ne sont autorisés.

## Validation et autorisation côté Rust

Avant tout accès protégé, l'API doit résoudre une identité vérifiée et son périmètre. Le frontend, une validation locale de la CLI et le proxy dashboard ne remplacent pas ce contrôle serveur.

| Contrôle cible | Refus attendu |
|---|---|
| Signature et clés | Algorithmes explicitement autorisés, clé compatible, signature valide ; refuser `none`, confusion de type de clé et algorithme non configuré. |
| Émetteur et destination | `iss` exact, audience de l'API présente, client émetteur autorisé selon le profil ; refuser token d'un autre realm, client ou service. |
| Temps et type | `exp` requis, `nbf` contrôlé s'il est présent, tolérance d'horloge bornée et publiée ; distinguer access token et ID token, refuser token expiré ou prématuré. |
| Profil de token | Figer champs et valeurs attendus, dont `typ`, `azp` ou `client_id` selon le contrat retenu ; refuser profil ambigu ou token d'une autre classe. |
| Autorisation | Résoudre memberships et permissions administrés côté serveur, puis appliquer le contrôle à chaque API, export, commande et flux SSE. |

Le [profil JWT access token RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html#section-4) impose notamment un type d'access token spécifique ; ne pas supposer qu'un token Keycloak par défaut suit ce profil. Le candidat accepte un profil précis : RS256, header `typ=JWT` avec `kid`, payload `typ=Bearer`, `iss`/`sub`/`aud`, entiers positifs `iat`/`exp`, `azp` égal au client public Web ou CLI configuré, `nbf` validé s'il existe. La fiche opérateur doit vérifier les tokens effectivement émis. Une compatibilité Entra ID ou autre OIDC arbitraire n'en découle pas ; les règles d'ID token ne sont pas transposées aveuglément aux access tokens.

Discovery et JWKS proviennent uniquement de la configuration de confiance de l'opérateur. Vérifier la cohérence exacte de l'issuer, TLS et les destinations autorisées ; borner taille, délais, redirections, concurrence et caches. Aucun `jku`, `x5u`, issuer ou autre URI fourni par un JWT utilisateur ne déclenche de requête réseau. Un `kid` inconnu ne permet qu'un rafraîchissement borné des clés de l'issuer déjà configuré, puis un refus si la clé reste inconnue. Le cache ne doit pas devenir un moyen de prolonger indéfiniment une clé. Voir [OIDC Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfig).

Le gateway et le dashboard actuels sont sur un réseau Docker interne sans route par défaut. Ils ne peuvent donc pas être supposés joindre un issuer externe. Le raccord exige soit un accès TLS strictement borné aux destinations IdP/discovery/JWKS nécessaires, soit une distribution contrôlée des clés publiques avec rotation qualifiée. Tout changement de frontière réseau doit être proposé avant réalisation ; aucun accès Internet général, proxy libre ou affaiblissement TLS n'est autorisé pour obtenir une connexion. Cette dépendance reste ouverte avant la qualification réelle.

L'identité humaine stable est le couple `(issuer, sub)` ; email et nom affiché restent des attributs modifiables. Le tenant et les permissions viennent d'associations administrées par le contrôle. Un attribut de profil éditable par l'utilisateur, un header, un paramètre ou un label worker ne choisit jamais le tenant. Une sélection de contexte ne peut choisir que parmi les memberships déjà vérifiés. Les groupes ou rôles signés de l'IdP ne valent que selon un mapping serveur explicite ; être administrateur Keycloak n'accorde aucun rôle ai-guard.

Les chemins de claims et valeurs de rôles/groupes externes mappés vers les permissions internes sont configurables et explicitement approuvés côté contrôle. Rust applique ce mapping seulement après validation du jeton d'accès destiné à l'API ; un mapping absent ou ambigu ne confère aucun privilège. Le rôle client externe `admin-ai-guard` est la valeur du profil de découverte, avec mapping explicite du claim du client API configuré ; ni ce nom ni un fournisseur ne sont imposés aux autres installations. Un nom de connexion ou un attribut de profil modifiable ne prouve aucun rôle. La portée administrative vient des organisations et tenants explicitement rattachés par le contrôle, sans accès inter-client implicite. Ce rôle n'accorde ni administration du realm, ni credential `runner`, ni contournement des politiques ou de l'audit. Le mode local nominatif doit offrir les permissions équivalentes sans IdP.

Les [vues utilisateur et administration unifiée](../ui.md#vues-utilisateur-et-administration-unifiée--cible-à-livrer) reposent sur un contrat typé de permissions, périmètres et configuration effectifs fourni par Rust. La vue personnelle expose les ressources propres ou explicitement partagées ; l'administration fournit la synthèse à 360° et les détails des utilisateurs, agents/sous-agents, sessions, sandboxes, workers/brokers, décisions, incidents, quotas, usage et configurations du seul périmètre autorisé. Distinguer contexte personnel et administration, ainsi que droits sur métadonnées, contenus, export et mutations ; aucune sélection locale « admin » ni visibilité de bouton ne constitue une autorisation.

Le contrôle agrège les ressources autorisées sans fusionner les bases tenants ni fournir de credential global au frontend. La synthèse peut couvrir plusieurs brokers ou tenants explicitement administrés ; elle conserve portée, provenance, fraîcheur et sources manquantes, sans dashboard par worker ni total extrapolé d'une page. Les URL directes, recherches, API, exports et flux SSE appliquent les mêmes permissions côté serveur. Ces vues et leur agrégation restent à implémenter et qualifier ; le dashboard `viewer` ne les livre pas.

Séparer utilisateur initiateur, acteur effectif et identité du broker/agent/sous-agent. Toute délégation lie parent, mission, tenant, permissions, expiration et révocation sans élévation implicite. Les workers n'obtiennent ni token SSO humain ni clé `runner` ; leur identité reste limitée au relais autorisé. Une action d'agent n'est pas automatiquement une instruction explicite de l'utilisateur. Une filiation seulement déclarée reste `declared`.

L'audit indépendant conserve identités, causalité, décision et effet observé avec leur provenance, sans bearer, code, vérificateur ou secret. Les contenus sont masqués avant persistance/diffusion ; accès, rétention, tailles et pertes sont explicites. L'indisponibilité de l'audit obligatoire refuse l'action, y compris une action déclenchée après connexion SSO.

Les points de contrôle signés et l'export vérifiable suivent le cahier produit ; leur mécanisme, la protection des clés et les limites de vérification restent à concevoir, implémenter et qualifier. Le chaînage historique des événements ne prouve pas à lui seul cette nouvelle exigence ni une observation runtime manquante.

## Durée de session, panne et déconnexion

Les tokens Web OIDC (`access_token`, `refresh_token`) restent exclusivement en mémoire vive, jamais dans URL, `localStorage`, `sessionStorage`, logs ou exports. Seul le nonce pré-remise éphémère sans autorité métier `correlation_token` (64 caractères hex minuscules, dont seul le condensat SHA-256 est conservé par le gateway) transite dans `sessionStorage` lié à l'origine complète (clé `aiguard.oidc.correlation_token`) entre `start()` et `/auth/oidc/complete`, et est immédiatement supprimé au début de `redeem()` ainsi que dans `close()`. Le gateway candidat conserve l'état PKCE privé en mémoire éphémère bornée puis le consomme ; une perte au crash impose une nouvelle connexion. Le code et `state` du callback sont transitoires : le gateway les consomme puis redirige vers `/auth/oidc/complete` sans ces paramètres. Empêcher leur fuite dans logs, télémétrie ou referrers reste obligatoire. Le vérificateur reste privé. La CLI conserve ses tokens dans son processus au premier plan, sans cache durable implicite. Le guide [Keycloak JavaScript adapter](https://www.keycloak.org/securing-apps/javascript-adapter) décrit le stockage mémoire et les contraintes des navigateurs ; il n'impose pas cet adaptateur au produit.

Le renouvellement est borné, coordonné entre requêtes et soumis à la session encore autorisée ; une réponse tardive ne reconnecte pas une session déconnectée. La politique des refresh tokens publics doit traiter rotation ou liaison cryptographique au client, ainsi que la détection de réutilisation, avec tests de concurrence. Expiration, refus de refresh et logout effacent l'état privé, annulent les requêtes et ferment les SSE. Le serveur vérifie la validité pendant les flux et les termine à expiration ou perte de permission selon une borne mesurée et publiée ; reconnecter exige une nouvelle vérification, avec curseur du même tenant autorisé. Une coupure produit un état déconnecté/périmé, jamais un faux zéro activité.

Un changement de rôle, de mapping, de membership, de périmètre ou d'utilisateur doit invalider les lectures et abonnements aux flux concernés et retirer les données devenues interdites, y compris les détails ouverts et caches. Les requêtes ou réponses tardives ne réintroduisent pas l'ancien contexte ; les requêtes devenues non autorisées sont refusées côté serveur. Le frontend actualise ses capacités depuis le contrôle ; sa seule fermeture de session ne remplace pas l'autorisation serveur. Cette prise en compte suit la politique de révocation et les bornes publiées, sans prétendre à une révocation JWT immédiate par la seule validation hors ligne.

La déconnexion locale doit fonctionner même si l'IdP est indisponible ; distinguer son succès d'une fermeture confirmée de la session IdP. Le candidat envoie un POST privé à l'endpoint end-session exact avec `client_id` et `id_token_hint` ; il n'implémente pas de redirect logout interactif. Configurer les redirects exacts si un mécanisme futur retenu les utilise, sans annoncer qu'un appel a révoqué toutes les copies d'un access token. Les possibilités discovery, clés, logout et révocation sont décrites par [Keycloak OIDC layers](https://www.keycloak.org/securing-apps/oidc-layers). Son introspection exige un client confidentiel ; elle ne justifie jamais de distribuer un secret au Web ou à la CLI publics.

Une validation JWT hors ligne ne garantit pas une révocation immédiate. Définir durées des tokens, validité du cache, rotation, révocation des mappings locaux et délai maximal de prise en compte. En panne IdP, un token encore valide et une clé de confiance encore valide ne peuvent être acceptés que selon cette politique explicite ; clé inconnue, cache périmé ou renouvellement impossible n'ouvrent aucun accès. Aucune panne SSO n'active automatiquement les anciennes clés ou un mode local. Le mode local nominatif hors ligne demeure un choix d'installation distinct, avec les mêmes contrats d'autorisation et d'audit.

## Fiche opérateur Keycloak à renseigner

Cette fiche est un inventaire de décisions, **pas le format de configuration du programme**. Le [guide SSO](../setup/sso/README.fr.md#préparer-le-json-privé-du-gateway) décrit le JSON fermé accepté via `--oidc-config`, l'initialisation exclusivement neuve avec `--initialize-oidc-audit` et la réouverture sans ce drapeau. Toutes les valeurs restent à renseigner pour le déploiement ; ne pas importer de credentials ou de realm existants implicitement. Le bundle public d'AC fournisseur est borné à 64 Kio / 8 certificats ; il ne configure pas automatiquement la confiance CLI→gateway. La politique originale exacte reste liée à l'audit ; aucune migration de cette politique ou commande CLI de sauvegarde/restauration de l'audit d'authentification n'est exposée.

| Élément | Valeur et preuve attendues |

## Deux procédures à livrer

**Découverte locale — profil IdP et connecteur candidat disponibles ; parcours réel NOT_RUN.** Le profil Compose opt-in limité au loopback, Keycloak épinglé, realm de démonstration et clients publics PKCE sont distribués. Les [guides SSO EN](../setup/sso/README.md)/[FR](../setup/sso/README.fr.md) documentent la configuration applicative et les mutations offline. Bootstrap complet des memberships/réseaux et recette réelle restent à livrer/qualifier. Quatre comptes publics sont propres à cette découverte :

| Compte | Identifiants publics de démonstration | Permissions attendues |
|---|---|---|
| Administrateur Keycloak | `admin / admin` | Administration du realm, sans droit ai-guard implicite |
| Administrateur ai-guard | `admin-ai-guard / admin-ai-guard` | Rôle client `admin-ai-guard` dans les claims mappés et vérifiés côté Rust, administration du seul périmètre de découverte |
| Utilisateur normal 1 | `user-1 / user-1` | Parcours Web/CLI sans rôle `admin-ai-guard` |
| Utilisateur normal 2 | `user-2 / user-2` | Parcours Web/CLI sans rôle `admin-ai-guard` |

Ces valeurs ne deviennent jamais les défauts d'une installation normale. Ne remplacer aucun credential, base ou volume existant ; aucun jeton SSO humain, credential d'administration Keycloak ou secret de contrôle ne rejoint un worker. Ne pas corriger un issuer incohérent par réécriture arbitraire ou désactivation de TLS ; les exceptions HTTP restent limitées au profil local explicitement isolé et au callback natif loopback prévu par le contrat.

La procédure devra diagnostiquer les prérequis, afficher les accès et leur disponibilité, connecter réellement `user-1` en Web et CLI, puis exécuter une action autorisée non destructive avec sa trace individuelle et son résultat réel. `user-2` doit être refusé sur les ressources privées du premier selon les périmètres établis par le contrôle. Le compte `admin-ai-guard` accède à l'administration autorisée ; les deux utilisateurs normaux en sont refusés côté Rust, et `admin` ne reçoit aucun droit applicatif implicite. L'accès du broker passe par la délégation explicite décrite plus haut. Mesurer le parcours, les interventions manuelles et séparément téléchargement/construction à froid et images présentes ; environ cinq minutes est une cible ergonomique, pas une durée garantie. Cette recette ne qualifie pas l'exploitation de Keycloak en production.

## Propriété de la transaction

Le premier lot local nominatif est implémenté et vérifié dans ses [gels logiciels ciblés](VALIDATION.md#1er-novembre--accès-humain-local-apicli-et-dashboard) : provisioning/reprise, memberships et grants, API/CLI de consultation/export et dashboard humain distinct du viewer. Au 2 novembre, le parcours Docker A/B API/CLI, export, redémarrage et révocation hors ligne passe sur l'image `954246…` issue de `7afdd43`, avec navigateur contre ce contrôle NOT_RUN. Un credential personnel prouve sa possession, pas la présence physique de son titulaire. Ce lot ne clôture ni le SSO, ni le lancement humain délégué, ni la chaîne complète agent/sous-agent ou l'audit signé. Les anciennes clés restent une classe distincte, sans réattribution rétroactive.

**Choix approuvé par le mainteneur le 1er novembre, implémenté comme candidat le 2 novembre : le gateway Rust possède les transactions PKCE Web et la validation OIDC.** Le dashboard assure un proxy d'authentification limité à des routes et destinations fixes. Paramètres privés en mémoire bornée, expiration, consommation atomique, rotation serveur inconditionnelle à `/start` du cookie opaque éphémère de corrélation sans token/verifier (sans émission préalable sur `/status`) ; échange côté Rust, puis remise unique au même navigateur et à l'origine initiatrice via la preuve pré-remise `correlation_token` (64 hex minuscules, vérifiée en temps constant contre son condensat SHA-256). Le cookie lie le navigateur sans fixer la transaction, et `correlation_token` lie la remise à l'origine complète sans valoir jeton métier. Aucun nouveau service ni cookie permanent d'authentification métier n'est décidé ; les tokens Web restent en mémoire. Une transaction perdue après crash exige une nouvelle connexion. Les protections CSRF, callbacks croisés, onglets, remise unique et nettoyage du callback font partie des critères d'acceptation, sans qualification navigateur déduite des tests contrôlés. Le stockage privé éphémère des paramètres PKCE et le passage transitoire du seul `correlation_token` en `sessionStorage` (supprimé dès `redeem()`/`close()`) restent distincts de l'interdiction de Web Storage pour les tokens.

En découverte explicitement activée, seul le gateway rejoint le réseau interne Keycloak existant, avec issuer identique pour navigateur, CLI et contrôle. Ni dashboard ni worker ne le rejoignent. L'exception HTTP reste limitée à cette démo isolée ; elle ne désactive pas TLS dans les autres profils. Aucun réseau n'a été raccordé ni flux OIDC exécuté par cette décision. Le contrat détaillé d'audit de connexion doit notamment traiter les sujets sans membership sans leur permettre de choisir un tenant.

Le token exchange est à évaluer pour la délégation vers une autorité d'exécution, avec droits, destinataire et durée bornés, sans transmettre le token humain au worker. Il ne remplace pas la connexion initiale PKCE. L'échange standard Keycloak demande un client confidentiel côté contrôle ; il n'est pas activé pour les clients publics Web/CLI par cette décision. Une capacité interne compatible avec l'installation locale sans IdP reste une alternative distincte, à contractualiser et tester. [Décision, sources officielles et limites](DECISIONS.md#1er-novembre--propriété-sso-approuvée-par-le-mainteneur).

La CLI Rust conserve sa propre transaction et ses tokens en mémoire, avec navigateur externe et listener loopback borné ; aucun cache durable implicite. Les guards de [api.rs](../../src/api.rs) conservent les restrictions générales et ajoutent les seules exceptions OIDC prévues pour le callback sollicité et l'origine Web exacte configurée. Leur comportement navigateur/IdP réel reste à qualifier, sans assouplissement global. Un issuer loopback joignable par le navigateur n'est pas automatiquement joignable par le gateway/dashboard conteneurisé : la fiche opérateur et la découverte doivent prouver les accès de chaque acteur en conservant le même issuer, sans réécriture ni ouverture réseau générale.
